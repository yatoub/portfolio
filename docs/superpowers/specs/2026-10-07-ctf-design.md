# Hidden CTF trail — design

Date: 2026-10-07 · Branch: `feat/lot-f-ctf` · Lot F

## Goal

Six flags hidden across yatoub.dev, each one reachable with a basic
reconnaissance technique. A standalone page, `/ctf/`, tracks the visitor's
progress locally and explains each technique once its flag is found. Same
spirit as `/whoami/`: educational, playful, the visitor does the work with
real tools against the real site.

This is the first of four feature ideas (CTF trail, Internet background
noise, request anatomy, network-observer view). The other three get their
own spec and are out of scope here.

## Decisions

| Question | Decision |
|---|---|
| Scope | All six flags. The two that need infrastructure (HTTP header, DNS TXT) are applied by the site owner; this repo only ships their hashes. |
| Discovery | Discreet hints, no navigation link. |
| Help level | Hint on demand per locked card; full explanation only once the flag is entered. |
| Validation | SHA-256 hashes in the page, never the flags themselves. |

## The six flags

Format: `YATOUB{...}`, ASCII, case-sensitive.

| # | `id` | Location | How it is found | Lesson shown once found |
|---|---|---|---|---|
| 1 | `robots` | `robots.txt` | Read `/robots.txt`: a comment carries the flag | The file is public and often maps what the owner would rather hide |
| 2 | `source` | `index.html` | View source: an HTML comment | Everything sent to the browser is readable |
| 3 | `dotfile` | Terminal overlay | `ls -a` reveals a hidden file, then `cat` | Hidden files are a display convention, not a protection |
| 4 | `curl` | `whoami/cli.txt` | `curl https://yatoub.dev/whoami`: the template adds the line only for a `curl` User-Agent | The server adapts to a header that is purely declarative, hence forgeable |
| 5 | `header` | HTTP response header | `curl -I https://yatoub.dev` or the Network tab: `X-Flag` | Response headers are invisible in the page but sent to everyone |
| 6 | `dns` | DNS TXT record | `dig +short TXT _ctf.yatoub.dev` | DNS is a public directory, TXT records included |

The repository is public, so flags 1 to 4 are readable in clear on GitHub.
That is accepted: reading the repository is one more valid technique. Flags
5 and 6 exist only on the server and in the DNS zone.

### Flags 5 and 6: values kept out of the repository

Their values are generated randomly during implementation and handed to the
site owner in the working session, together with:

- the Caddy line for `conf.d/lab.caddy` (repo `homelab-ansible`):
  `header X-Flag "<value>"` on the site block;
- the DNS record: `_ctf.yatoub.dev. TXT "<value>"`.

Only their SHA-256 hashes are committed. The values must not appear in code,
tests, this spec, the plan, commit messages or the vault note.

## Discovery hints

- `robots.txt`: the comment holding flag 1 also mentions `/ctf/`.
- `curl.txt`: one line in `tools/curl.tpl.txt` (regenerated by `build.mjs`).
- Terminal: `ctf: '/ctf/'` added to `SECTIONS` in `term/core.js`, and `ctf`
  added to the `open` entry of `term.help` in both languages.
- `index.html`: a comment near the top of the source points to `/ctf/`
  (distinct from the comment holding flag 2, placed further down).

The page carries `<meta name="robots" content="noindex">` and is not added
to `PAGES` in `tools/build.mjs`, so it stays out of `sitemap.xml`. It is not
linked from the navigation.

## The `/ctf/` page

Standalone page, same shape as `whoami/` and `status/`:

```
ctf/index.html        structure, data-i18n attributes
ctf/styles.css        page styles, palette and fonts from the design system
ctf/translations.js   FR/EN strings: titles, hints, explanations, messages
ctf/core.js           pure logic, no DOM (tested)
ctf/script.js         DOM: rendering, form, language toggle, storage
```

Layout, top to bottom:

1. Header in the terminal style (`$ ./ctf --progress`) with a progress bar
   and an `n/6` counter.
2. One input and a submit button. The hash of the submitted value selects
   the card it unlocks; the visitor never says which flag they found.
3. A status line under the form: found, already found, or not a flag.
4. Six cards in the order of the table above.
   - Locked: index, evocative title, a button revealing one hint.
   - Found: index, title, explanation of the technique, the command to
     reproduce it, and what an administrator takes from it defensively.
5. At 6/6: a closing message with the contact link, and a reset button
   (reset is available at any time, behind a confirmation in the page, not
   a browser dialog).

Language: FR/EN, auto-detected, shared `localStorage 'lang'` key, `[FR|EN]`
toggle as on the other standalone pages. All text is set with `textContent`.
French strings containing apostrophes use double-quote delimiters.

Visual direction: Catppuccin Mocha variables and JetBrains Mono / Orbitron
from `/assets/`, cards consistent with `/whoami/`. No new palette.

## `ctf/core.js`

Exposed as a global `CtfCore` (same pattern as `TermCore`), with a CommonJS
export guard for the tests.

- `FLAGS`: ordered list of `{ id, hash }`, `hash` being the lowercase hex
  SHA-256 of the flag.
- `normalize(input)`: trims surrounding whitespace. Nothing else: case and
  inner characters are significant.
- `sha256Hex(text, subtle)`: hex digest through the given `SubtleCrypto`
  (the browser's `crypto.subtle`, or Node's `webcrypto.subtle` in tests).
- `check(input, subtle)`: resolves to the matching `id`, or `null`.
- `parseProgress(raw)`: turns the stored string into a list of known ids,
  dropping duplicates and unknown ids; invalid JSON yields an empty list.
- `serializeProgress(ids)`: the inverse.

`crypto.subtle` requires a secure context: HTTPS in production, `localhost`
in development. If it is unavailable, the page says so instead of failing
silently.

## Progress storage

`localStorage 'ctf'` holds the JSON list of found ids, never the flags.
Every access is wrapped in `try/catch`: when storage is unavailable
(private browsing, blocked site data) progress lives in memory for the
session and the page still works.

## Terminal changes (`term/core.js`)

- `buildFs` adds a dotfile at the home root holding flag 3.
- `ls` accepts `-a` (and combined short options containing `a`). Without
  it, entries starting with `.` are omitted from listings.
- Completion omits dotfiles unless the typed prefix starts with `.`.
- `cat` and `cd` resolve dotfiles regardless: hiding is display-only, which
  is the lesson of flag 3.

## `whoami/cli.txt`

The template appends a flag line when the request's `User-Agent` starts with
`curl/`. Other clients, including a browser opening `/whoami/cli.txt`
directly, get the current output unchanged. The `Cookie` / `Authorization`
redaction is untouched.

## Tests and CI

- `tools/ctf-core.test.mjs`:
  - `normalize`, `check` (match, no match, surrounding whitespace, wrong
    case), `parseProgress` (invalid JSON, unknown ids, duplicates).
  - Consistency: the test reads `robots.txt`, `index.html`, `term/core.js`
    and `whoami/cli.txt`, extracts the `YATOUB{...}` each contains, and
    asserts its hash equals the declared one for `robots`, `source`,
    `dotfile` and `curl`. Changing a flag without its hash fails CI.
  - `FLAGS` holds exactly six entries with distinct ids and 64-hex hashes.
  - Hint and explanation strings exist for every id in both languages.
- `tools/term-core.test.mjs`: `ls` hides dotfiles, `ls -a` shows them,
  `cat` reads the dotfile, completion behaviour, `open ctf`.
- `.github/workflows/deploy.yml`: `ctf/*.js` added to the syntax-check loop.
- Tests must pass under Node 22 (the CI runner version).

Not testable locally: flags 4, 5 and 6 need the real Caddy and DNS. They
are verified on production after deployment with the three commands from
the table.
